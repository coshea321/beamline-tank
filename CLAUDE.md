# Beamline Tank

LaserTank-style puzzle game. Plain JS, no dependencies. Played on GitHub Pages
(**live game: https://coshea321.github.io/beamline-tank/**), an installable PWA served from `docs/` on `main`. The old claude.ai artifact is retired: don't update it.
Cathal is a **non-coder**: he reviews and merges every PR. Lead with the answer, be concise, flag honest trade-offs.

## Docs
- `HANDOVER.md`: rules as implemented, level format, file map, deploy steps. **Read it before changing rules, levels or the build.**
- `BACKLOG.md`: pending ideas and decisions on record. Check it before proposing a feature.

## Commands
- `npm run solve`: par + shortest solution for every level (`npm run solve -- crate` for one).
- `npm run build`: solves every level (fails if one is unsolvable), bakes in PAR, writes `docs/` (PWA) and `build/artifact.html`.
- `npm run check`: Playwright smoke test of the built PWA (script errors, service worker, offline reload, tap-to-drive, tap-to-shoot, collapsible sector strip and its groups, level switch mid-animation).
  Playwright and Chromium are preinstalled in Claude Code web sessions.
- `node tools/try.js ./scratch.js`: solve a scratch file of candidate levels.
- `node tools/batch.js 10 <seed>`: 10 new extra-hard levels from scratch, checked and inserted (about 75 min). See HANDOVER.md.

## Rules
- Edit `src/` and `pwa/` only. `docs/` and `build/` are generated by `npm run build`; never hand-edit them,
  but **commit them with every source change** (CI rebuilds and fails if they don't match).
- `src/engine.js` is shared by the browser and the Node solver. Keep it DOM-free and side-effect-free apart from mutating the state passed in.
- After any change to engine rules or levels, run `npm run solve`; every level must stay solvable. `npm run build` refuses to build otherwise.
  A rule change that moves the par of levels it wasn't meant to touch is a bug until proven otherwise.
  The rules chosen where the original game was unclear are decisions on record (`BACKLOG.md`): confirm with Cathal before changing one.
- New levels: try them with `node tools/try.js ./scratch.js`, read the shortest solution for unintended shortcuts, then add them to `src/levels.js` in difficulty order with a short `tip`.
- All colors are CSS tokens in `src/shell.html` (light + dark). The canvas reads them at runtime; don't hard-code colors in `ui.js`.
- Saved progress is keyed by level name (localStorage `blt2`), so renaming a level resets its solved mark.
- Verify UI changes with `npm run check` (Playwright) before committing.
- The header shows `version` from `package.json` (e.g. `v1.1`). Bump it in every PR players will notice (1.1 → 1.2; 2.0 for a big change). The service worker cache is stamped separately from a hash of the page.
- Confirm the design of anything non-trivial before building it, then build the confirmed scope: no wider, no narrower.

## Changes and pull requests
- Never push to `main`. Every change goes through a PR into `main`; after a PR is merged, restart the working branch from `origin/main` before new work. One PR per change.
- `/release` (`.claude/skills/release/SKILL.md`) runs the solve → build → docs → check → commit → push → test link → PR tail.
- PR bodies follow `.github/pull_request_template.md` (the API doesn't apply it): a "Try this version" link first
  (this branch's `build/artifact.html` published as a separate test artifact, never the live one before merge), then the live game link,
  then plain-English boxes for what to tap. CI (`.github/workflows/checks.yml`) runs build, the build-output match and `npm run check` on every PR.
- Merging is the release: Pages redeploys `docs/` from `main`. No artifact to update afterwards.
- After significant work, update `HANDOVER.md` (rules, file map, level count) and `BACKLOG.md` (strike what closed, record decisions).
